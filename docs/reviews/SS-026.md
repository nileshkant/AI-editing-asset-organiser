## Behavior and acceptance evidence

- Explicit `files` scopes enroll canonical contained file entries; folder sources retain recursive discovery. Single drops, multi-file selection, repeated paths, nested parents in either order, identical content at different paths and files inside existing recursive sources retain independent sound identity without importing siblings. `file_scopes.rs` covers membership enforcement and identity; real FFmpeg fixtures establish discovery and cache reuse.
- Jobs persist exact relative targets. Recovery and reconciliation use those targets, including a single file selected inside a recursive folder. Two real native-worker tests exercise duplicate submissions, separate progress for files sharing a parent and restart with an unqueued sibling selection. The queue admits at most 32 active jobs; batches admit at most 256 paths. Duplicate queued/running submissions share their job and scheduled work.
- Unsupported extensions are rejected by the shared core with an explicit reason. Extensionless media is accepted for actual decoder verification. Corrupt media produces per-file analysis errors. Both file-picker and drag/drop UI loops continue after individual failures, deduplicate paths and reject oversized batches; drop submission stops on unmount.
- Settings shows recursive versus selected-file scope and per-entry pending/ready/failed/missing/offline availability, with 100-entry pages. Scope conversion and removal require a focus-contained confirmation dialog with Escape/cancel and focus restoration. Core callers must also supply confirmation. Removing a scope deletes catalog annotations/recipes without deleting original media. Overlapping scopes prevent recursive conversion until the other scope is relinked or explicitly removed; nested explicit selections themselves are supported.
- Verified single-file relink handles renames and parent relocation without decoding or changing sound IDs, analysis, annotations or recipes. A sole-file scope retains its source ID when its parent changes; moving one member from a shared scope retains the sound ID and transfers membership to the destination scope. Whole-parent relink preserves the original source ID and verifies only registered members. Replacement mismatch, destination collision and stale catalog generation reject without committing changes. Native file relink captures identity under the catalog lock, hashes outside it, then validates identity/generation on commit.
- Complete selected-file reconciliation marks only absent selected sounds missing. Partial discovery and cancellation do not reconcile. Cancellation also clears persisted queued work. Offline roots are reported separately from missing individual files. Original bytes and cached profile preservation are asserted in relink/removal tests; Unix symlink escapes are rejected before enrollment.
- Export indexing uses the same explicit file-enrollment service. A new export destination enrolls just the generated file, and an existing selected scope stays explicit; output resolution and independent identities are tested with actual FFmpeg output.
- Schema v5 adds source scope, explicit entries and job targets. Existing folders retain IDs, analysis, annotations, favorites, recipes and queued jobs. File-backed upgrades first create a compatible pre-v5 SQLite backup; migrations commit transactionally. Tests cover preserved data, readable backups and rollback on migration failure. The older saved-search migration fixture was corrected to contain the real v2 jobs/analysis schema rather than an unrelated profiles table.

The UI/shared-core half of the final acceptance criterion is verified. Live MCP serialization and availability retrieval remain unverified because SS-018/SS-019 have not implemented the MCP service. The ticket retains its unchecked MCP criterion; this PR does not claim an operational MCP adapter.

## Optimization evidence

Registration uses indexed source-generation/scope/cache-existence checks rather than loading every selected entry or deserializing profiles per file. Internal source selection/search uses lightweight source headers. Reconciliation uses hash-set membership rather than scanning the entire seen vector for each catalog row. Queue messages retain source IDs instead of snapshots of every selected entry; workers read the current source at execution.

On local macOS in the debug build, the 10,000-path fixture measured **280.7 ms** for the former vector-membership operation alone versus **9.4 ms** for the new reconciliation including its SQL query and transaction. This is a local microbenchmark with different included work, not an end-to-end or universal speed claim. The existing 100,000-sound search benchmark budget is unchanged and remains passing.

## Windows CI correction

The first final-head run (`92cfc0f`) passed macOS/Linux but failed the v4 migration fixture on Windows with `duplicate column name: scope`. The fixture had derived v4 SQL using newline-sensitive replacements on the current v5 schema; Windows CRLF checkout left the new column in that supposedly old database. Replaced it with the actual historical v4 schema from merged main `1e04fb8`, shared by the v2 fixture without column-removal substitutions. The preservation/backup test now runs the historical SQL with both LF and CRLF line endings on every platform. Production migration logic was unchanged; no test was skipped and no assertion or performance budget was weakened.

## Search performance CI correction

Revision `4cfb575` passed Windows and Linux, including both migration fixtures. Its macOS job passed the migrations but measured 647 ms against the unchanged 600 ms debug search limit. Replaced repeated linear synonym-group scans in token canonicalization with one immutable, lazily initialized alias lookup. A regression checks every configured alias and unchanged unknown/Unicode words; the existing search behavior suite covers ranking, synonyms, typo correction, exclusions and accent matching.

The same local 100,000-sound benchmark measured 283 ms immediately before this change and 199 ms afterward in debug, and 41 ms in release. The original 600 ms debug / 100 ms release limits are unchanged. The full real-media Rust regression suite was rerun after the change.
