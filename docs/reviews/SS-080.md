## Measurements (release build, Linux container, 100,000 images)

The first implementation scanned every row in path order and joined each to its
annotations. That took about 600 ms per call whatever the filter, and almost
all of it was the per-row lookup. Search now uses two plans:

- Without filters, the gallery index serves the page directly.
- With filters, it does two sequential scans (annotations in storage order, then
  order and path from the covering gallery index), joined in memory on the
  128-bit image ID. Only matches are kept, and nothing is sorted afterwards.

| Call | Before | After (median) |
| --- | --- | --- |
| `images.search`, first page, no filter (end to end) | 662 ms | 23 ms |
| `images.search`, text, 1% match (end to end) | 607 ms | 181 ms |
| `images.search`, text, no match (end to end) | 601 ms | 155 ms |
| `images.search`, untagged, page at offset 99,000 (end to end) | 601 ms | 165 ms |
| Catalog filter only: none / deep page / tag / text | — | 15 / 49 / 77 / 98–143 ms |

The end-to-end numbers include building 50 result items. The container's
timings vary by about ±30% between runs. Commands:
`SS080_IMAGES=100000 cargo test --release -p soundshelf-core --test agent_images -- --ignored --nocapture`
and `cargo test --release -p soundshelf-core --lib filtered_search_cost -- --ignored --nocapture`.

## Review findings and fixes

- Search was 600 ms at the catalog cap; fixed as above.
- Opaque previews are JPEG, not PNG. The test and the contract now say so.
- Undo is single-step by design: undoing an older client edit after a newer one
  is a conflict. The test checks the latest undo only.

## Remaining limits

- Search is a substring match, not ranked. Ranking and facets are SS-067.
- No bulk tagging tool: a client tags one image per call. Bulk is SS-068.
- External AI clients were not exercised; the tests use the official SDK client.
